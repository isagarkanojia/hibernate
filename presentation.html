What is JDBC?

JDBC (Java Database Connectivity)

  • Java API for connecting to relational databases
  • Provides methods to query and update data
  • Database-independent abstraction layer
  • Part of Java SE (java.sql package)
Key Components:
  • DriverManager
  • Connection
  • Statement/PreparedStatement
  • ResultSet

JDBC Example - Statement ⚠️ Not Safe

Direct SQL execution - vulnerable to SQL injection

// ❌ Vulnerable to SQL Injection
public List getCustomersWithHighRiskScore() {
    List customers = new ArrayList<>();
    String sql = "SELECT * FROM customer WHERE risk_score > 710";

    try (Connection conn = dataSource.getConnection();
         Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery(sql)) {

        while (rs.next()) {
            Customer customer = new Customer();
            customer.setId(rs.getLong("id"));
            customer.setName(rs.getString("name"));
            // ... manual mapping
            customers.add(customer);
        }
    }
    return customers;
}
Problems: SQL Injection • Manual Mapping • Boilerplate Code

JDBC Example - PreparedStatement ✅ Safe

// ✅ Safe from SQL Injection
public List getCustomersWithRiskScore(int riskScore) {
    String sql = "SELECT * FROM customer WHERE risk_score > ?";

    try (Connection conn = dataSource.getConnection();
         PreparedStatement pstmt = conn.prepareStatement(sql)) {
        
        pstmt.setInt(1, riskScore);  // Parameter binding
        
        try (ResultSet rs = pstmt.executeQuery()) {
            // ... mapping
        }
    }
}
Advantages:
✅ SQL injection protection
✅ Better performance
Still Problems:
❌ Manual mapping
❌ Repetitive code

public interface CustomerRepository

@OneToMany

⚡ Hibernate Caching

Two-Level Performance Optimization

Hibernate Caching Overview

⚡ First-Level Cache (L1)
Session/Transaction • Enabled by default • Cannot disable
↓
🚀 Second-Level Cache (L2)
Application-wide • Optional • Shared across sessions
↓
💾 Database
💡 Why Caching?
✅ Reduce DB round trips ✅ Improve performance ✅ Lower DB load

⚡ First-Level Cache (L1)

Session/Transaction-Scoped Cache

✅ Characteristics:
  • Enabled by default
  • Cannot be disabled
  • Transaction-scoped
  • Automatic management
  • Identity guarantee
  • Dirty checking
💡 Key Insight:
All objects with same ID within a transaction are the SAME instance in memory! 
@Transactional
public void demo() {
    // First fetch - DB hit
    Customer c1 = repo.findById(1L).get();
    
    // Second fetch - Cache hit! 🎯
    Customer c2 = repo.findById(1L).get();
    
    // Third fetch - Cache hit! 🎯
    Customer c3 = repo.findById(1L).get();
    
    // Same object reference!
    System.out.println(c1 == c2); // true
    System.out.println(c2 == c3); // true
}
⚠️ Important: Cache cleared when transaction ends!
🔄 Dirty Checking Example: 
@Transactional
public void update() {
    Customer c = repo.findById(1L).get();
    c.setName("Updated Name");  // Just modify - no save() needed!
    // Hibernate detects changes and executes UPDATE automatically on commit!
}

🔍 First-Level vs Second-Level Cache

Understanding the Differences

Feature First-Level Cache (L1) Second-Level Cache (L2)
Scope Session/Transaction Application-wide
Sharing Not shared between sessions Shared across all sessions
Lifecycle Dies with transaction Survives transactions
Configuration Enabled by default Must enable explicitly
Can Disable? No Yes
Storage In-memory (JVM) External provider (EhCache, Redis)
Use Case Within single transaction Across application
L1 Best For:
  • Same entity multiple times in one transaction
  • Dirty checking within transaction
L2 Best For:
  • Read-heavy reference data
  • Entities accessed across requests

🚀 Second-Level Cache (L2)

Application-Wide Shared Cache

💎 Characteristics:
  • Shared across ALL sessions
  • Application-scoped
  • Survives transactions
  • Optional (must enable)
  • Requires external provider
  • Configurable strategies
📊 Cache Strategies:
  • READ_ONLY - Immutable data
  • READ_WRITE - Most common
  • NONSTRICT_READ_WRITE - Faster
  • TRANSACTIONAL - JTA only
⚙️ Setup (3 Steps): 

<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-jcache</artifactId>
</dependency>
<dependency>
    <groupId>org.ehcache</groupId>
    <artifactId>ehcache</artifactId>
</dependency>
# 2. Enable in application.properties
spring.jpa.properties.hibernate.cache.use_second_level_cache=true
spring.jpa.properties.hibernate.cache.region.factory_class=
    org.hibernate.cache.jcache.JCacheRegionFactory
// 3. Annotate Entity
@Entity
@Cacheable
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Customer { ... }
🎯 Performance Impact:
Transaction 1: DB Hit → Cache Store
Transaction 2+: Cache Hit → NO DB! 🚀

⚠️ Common Pitfalls

Performance Killers & How to Fix Them

Common Pitfall #1: N+1 Problem

The Silent Performance Killer

// Query 1: Fetch all customers
List<CustomerWithLoans> customers = repo.findAll();

// Query 2-N: Fetch loans for EACH customer 💥
for (CustomerWithLoans customer : customers) {
    customer.getLoanApplications().size(); // N queries!
}
SQL Generated: 
SELECT * FROM customer;
SELECT * FROM loan WHERE customer_id = 1;
SELECT * FROM loan WHERE customer_id = 2;
-- ... N more queries!
Impact:
  • 10 customers = 11 queries
  • 1000 customers = 1001 queries 📉

N+1 Problem - Solutions

Solution 1: JOIN FETCH (Recommended) ⭐ 
@Query("SELECT DISTINCT c FROM CustomerWithLoans c " +
       "LEFT JOIN FETCH c.loanApplications")
List<CustomerWithLoans> findAllWithLoans();

✅ Result: 1 query total (not 1+N)

Solution 2: @EntityGraph 
@EntityGraph(
  attributePaths = {"loans"})
List<Customer> findAll();
Solution 3: @BatchSize 
@OneToMany
@BatchSize(size = 10)
List<Loan> loans;
Performance: 1001 queries → 1 query 🚀

Common Pitfall #2: Inefficient SQL

When Hibernate Generates Suboptimal Queries

❌ Inefficient JPQL (Correlated Subqueries) 
SELECT c.id, c.name,
    (SELECT COUNT(*) FROM loan WHERE customer_id = c.id),
    (SELECT SUM(amount) FROM loan WHERE customer_id = c.id)
FROM customer c

Each subquery runs for EVERY customer! O(N) complexity 💥

Problem: 100 customers = 200 subquery executions!

Inefficient SQL - Solution

✅ Efficient Native SQL (JOIN + GROUP BY) 
SELECT c.id, c.name,
    COUNT(la.id) as loan_count,
    COALESCE(SUM(la.requested_amount), 0) as total
FROM customer c
LEFT JOIN loan_application la ON c.id = la.customer_id
GROUP BY c.id, c.name

Single query • Database-optimized • O(1) complexity 🚀

✅ Benefits:
  • 1 query vs N queries
  • DB-optimized JOINs
Use Native SQL for:
  • Complex aggregations
  • Window functions
  • Performance-critical
